# Development

Everything needed to run, change and deploy the site.

## Commands

| Command                | What it does                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------- |
| `npm install`          | Install dependencies (Node 22 or newer)                                                |
| `npm run dev`          | Start the dev server, proxying `/api` to a local tax-service                           |
| `npm run dev:mock`     | Start the dev server with saved responses, no tax-service needed                       |
| `npm test`             | Run the tests once                                                                     |
| `npm run check`        | Lint, format check, type check and tests                                               |
| `npm run format`       | Format all files                                                                       |
| `npm run build`        | Write the static site to `dist/`                                                       |
| `npm run api:generate` | Regenerate the API types from `api/openapi.yml`                                        |
| `npm run api:sync`     | Copy tax-service's published spec into `api/openapi.yml` (needs `gh`), then regenerate |

## API client

`api/openapi.yml` is a copy of the spec tax-service publishes (`openapi/openapi.yml` on its main). Types in `src/api/generated/` are generated from it and committed; CI fails if they are stale, or if the copy differs from tax-service's current spec (run `npm run api:sync` to update both). The drift check runs on every push to main, daily, and on every pull request, including from forks. It fetches tax-service's published spec without a token and fails if the download fails or the files differ. Never edit either by hand.

`src/api/client.ts` is a thin hand-written client for the two endpoints: `listJurisdictions` and `computeTakeHomeCalculation`. Money stays a decimal string everywhere. Errors throw `ApiError` (with the RFC 9457 problem body) or `NetworkError`.

The API location is `VITE_API_BASE_URL` at build time: the full prefix in front of the spec's paths (for example `https://api.example.com/api/v1`). Unset, it is `/api/v1`, meant for a dev server that proxies `/api` to a local tax-service.

## Local development

Two ways to run the page, both with `npm run` from this folder.

**Real figures** (`npm run dev`): start tax-service in its own checkout with `./dev.sh` (it listens on `http://localhost:8000`). The dev server forwards every `/api` request to it, so there is no CORS setup and the answers are the engine's own. If tax-service runs somewhere else, set `DEV_API_TARGET`, for example `DEV_API_TARGET=http://localhost:9000 npm run dev`.

**No backend** (`npm run dev:mock`): Mock Service Worker answers in the browser from `src/api/fixtures/`, the saved engine output for $70,000 in Ontario (2025 gives take-home 53,468.68; 2026 is provisional). Any valid salary gets those same figures (the jurisdiction and language are ignored; year 2026 gets the 2026 answer, every other year the 2025 one); a salary the API would reject gets the saved validation error, whose text is fixed. The mock layer is not part of the built JavaScript.

**Tests** use the same handlers: `import { server } from './mocks/server'` (path relative to the test), call `server.listen()` before the tests, `server.resetHandlers()` after each and `server.close()` at the end (see `src/mocks/handlers.test.ts`), and override a response with `server.use(...)`.

There is no fake server generated from the spec (it would invent figures, which is wrong for a tax tool). `public/mockServiceWorker.js` is MSW's own worker file; it is generated by `npx msw init public --save=false` and not edited by hand.

## Lint rules

`npm run lint` enforces the architecture doc's layering. Each folder under `src/` may import only what the folder table allows: `api`, `money` and `theme` import nothing else in `src`; `adapters`, `money`, `theme` and `api` never import React; components may use `api` and `adapters` for types only (`import type`) and never `mocks`; only `src/main.tsx` and tests import `src/mocks`. Money stays text: `Number`, `parseFloat`, `parseInt`, `.toFixed(` and `Intl.NumberFormat` are banned everywhere except `src/money/` (and `src/styles/`, which holds the colour maths of the token test). Dynamic `import()` is held to the same layer rules. Components also get `eslint-plugin-jsx-a11y` (its recommended set does not flag a bare `<input>` with no label, only a `<label>` tied to nothing or an image without alt text, so Testing Library's by-role queries remain the check for unlabelled inputs), and all code gets typescript-eslint `strictTypeChecked` with `noUncheckedIndexedAccess` and `verbatimModuleSyntax` in `tsconfig.json`. `build/eslint-rules.test.js` lints a small example for each rule, so a rule that stops firing fails the tests. Node 22 is pinned in `.nvmrc`. `package.json` has an `overrides` entry for `eslint-plugin-jsx-a11y` because its declared ESLint peer range lags ESLint 10; the plugin works with it, so do not remove the entry without checking.

## Deploying

Every merge to main publishes the site to dev (`.github/workflows/deploy-dev.yml`): a build job with no cloud credentials runs tax-engine and npm with `VITE_API_BASE_URL=https://api-dev.aftertaxlens.com/api/v1` and hands `dist/` to a deploy job as a workflow artifact; the deploy job, which holds the role, runs no npm, Python or repository script, uploads `dist/` to the dev bucket and refreshes the CDN (the same shape as prod, below). Hashed files under `assets/` are cached for a year; everything else is fetched fresh each time, so a bad build is replaced by the next merge. No keys are stored: the workflow takes a short-lived role (OIDC) that tax-infra creates, trusted for this repository's main branch only, and able to do nothing but upload and remove files in that bucket and refresh that distribution.

The workflow does nothing until three repository variables are set (not secrets; none of them is secret) from tax-infra's outputs once the dev site exists: `AWS_SITE_DEPLOY_ROLE_ARN_DEV` (`site_deploy_role_arn`), `SITE_BUCKET_DEV` (`site_bucket_name`) and `SITE_DISTRIBUTION_ID_DEV` (`site_distribution_id`). Dev answers at https://dev.aftertaxlens.com and asks search engines not to index it. The API allows calls from that address only (CORS in tax-service, set by tax-infra from the site name), and the site's Content-Security-Policy allows calls to the dev API only, which is why the build must keep scripts in files. The API address in the workflow and tax-infra's `api_domain_name` for dev must stay the same; change them together.

Prod publishes only when a GitHub release is published with a tag like `v1` or `v2` (`.github/workflows/release.yml`, a trigger that calls `release-publish.yml` as it is on main; build and deploy are two jobs in that one file). The build job has no cloud credentials and builds with `VITE_API_BASE_URL=https://api.aftertaxlens.com/api/v1` and `VITE_SITE_URL=https://aftertaxlens.com`, so the prod API must be up first (the build calls it once, for the list of jurisdictions it serves; the figures come from the local engine, see "Salary pages"). The deploy job waits for approval in the `prod-deploy` environment, never runs npm, uploads the build in the dev order and, after the stale assets are deleted, refreshes the whole CDN. It reads `AWS_SITE_DEPLOY_ROLE_ARN_PROD`, `SITE_BUCKET_PROD` and `SITE_DISTRIBUTION_ID_PROD` from that environment (not secrets) and ends green without deploying while they are unset. A release is refused unless its commit is already on main.

## Dependency updates

Dependabot version updates (`.github/dependabot.yml`) arrive monthly, as one pull request each for production npm packages, development npm packages and GitHub Actions. Security updates are separate and can arrive at any time. They go through the normal review and merge; nothing merges itself.

## Search and sharing (SEO)

The title, description, Open Graph and Twitter card tags, theme colours and the static heading and intro inside `#root` are plain text in `index.html`; a test (`build/index-html.test.ts`) checks them against `src/strings.ts`. Values that differ per environment come from `VITE_SITE_URL` (the public address, origin only, no path, for example `https://aftertaxlens.com`) through `build/seo.ts`: at build time it adds the canonical link, `og:url` and the absolute share-image address with its size and description, and writes `robots.txt` and `sitemap.xml`; each sitemap entry carries a `lastmod` that moves only when that page's HTML changes (see the salary pages below; the dates need the engine file too, and without it the sitemap lists the calculator alone, undated). Unset, as in local development, those are left out and the sitemap is not written. The share image is `public/share-card.png` (1200 by 630, no figures). Keeping the dev hostname out of search results is done at the CDN, not here.

## Pre-built salary pages

A deploy build can write one finished page per province and salary step (for Ontario, `dist/ca-on/30000/index.html` to `dist/ca-on/150000/index.html` in $5,000 steps), so a search engine sees the real answer without running JavaScript. The provinces, their year, salary range and step are one list in `build/salaryPages/provinces.json` (read by `build/salaryPages/provinces.ts` and by the Python step); adding a province is one new entry, and a listed province the API does not return is handled by the kind of build: with `VITE_SITE_URL` set (a prod-shaped build) the build fails naming each such province and its code, before any call for a page and before writing anything, and without it the build warns and skips that province. Every figure on the pages comes from tax-engine run locally, not from an API. A deploy job first runs `build/localEngine/resolve_pin.py`, which reads the `tax-engine==` line of the public tax-service's `requirements.txt` by commit sha (`main` for the dev deploy and CI, the latest `v<number>` release tag for a release) and writes a requirements file with that version and the hashes PyPI lists for it (any failure, such as no line, two lines or an unknown release, fails the build; it never falls back to the committed file), installs it with `--require-hashes --only-binary=:all:` (the hashes protect the download, not against a bad release, until tax-service publishes its own hashed requirements, tax-service #91), runs `python -I build/localEngine/engine_figures.py build/salaryPages/provinces.json <file>` once per salary and writes one JSON file, then runs `npm run build` with `ENGINE_FIGURES_FILE` naming it. The script asks tax-engine's own take-home function (`build_take_home`, the one tax-service serves the calculator with) for every salary and writes its answer in the API's shape, with no mapping of its own, so the figures equal the live calculator's: the site follows the engine release tax-service pins, with nothing to bump by hand. A release of tax-service that is tagged but not yet deployed makes the next frontend release pick its engine early, so release the service first. The committed `build/localEngine/requirements.txt` (and `requirements.in`) stays for running the step by hand and as the Dependabot anchor; a deploy takes only its PyYAML pin (the engine's one dependency, installed with `--no-deps`), so a Dependabot bump of PyYAML there does change what deploys install, while the tax-engine version never comes from it. The Node build checks every answer against `api/openapi.yml` (`build/localEngine/read.ts`) and the page guard, so a shape that drifts from the service fails the build. `provisional` is the service's policy, not the engine's, so the build adds it from the one API call it still makes, `GET /jurisdictions`, which also says which provinces are served: with `VITE_SITE_URL` set (a prod-shaped build) a listed province the API does not return fails the build naming each such province and its code before anything is written, and without it the build warns and skips that province. The same file also holds the hub-chart sweep (see below). To try it by hand: `pip install --require-hashes --no-deps -r build/localEngine/requirements.txt` (or run `resolve_pin.py main build/localEngine/requirements.txt <file>` and install `<file>`), run the script as above, then `ENGINE_FIGURES_FILE=<file> VITE_API_BASE_URL=<api> npm run build`. Without `ENGINE_FIGURES_FILE`, as in local development and CI's build, no salary pages are written. Each page is the real app rendered to HTML (`build/salaryPages/prerender.tsx`) plus one JSON data block that React reads on load (the advanced view's forms and lines are in the page too, inside a closed `<details>`, so a crawler reads them; `build/salaryPages/advancedHtml.test.ts`), so opening a page makes no API request; changing the salary and pressing Calculate calls the API and updates in place. With `VITE_SITE_URL` set, `dist/sitemap.xml` is rewritten after the pages to list the calculator and exactly the pages that were written, each with a `lastmod` date that moves only when that page's HTML changes: the build hashes every finished page (the calculator included) into `dist/page-hashes.json`, with the addresses of the built script and style files under `/assets/` replaced by one fixed token first, so a release that changes only code does not move any date but a changed figure, title or text does; the file lists path, SHA-256 and date for each page, and the build compares it with the live site's copy at `VITE_SITE_URL`, keeps the old date for an unchanged hash and gives a changed or new page today's UTC date; on a first build, or when the live file is missing or unreadable, every page gets today's date and the build warns instead of failing. Pages therefore carry no timestamps. Each page's `<link rel="canonical">` and `og:url` are its own address (`build/salaryPages/address.ts` builds the address for the sitemap, the canonical and the links alike); unset, there is no sitemap and no canonical. Each page also links, with plain `<a href>` links in a `nav`, to the previous and next salary, the calculator and the nearest other pages of its province; the links are built from the pages about to be written, so none points at a missing file, and they travel in the data block so the static page and the mounted page match. On a salary page the answer comes first, in the source and on screen: the heading, then the take-home figure with its breakdown, then the provisional-year note when there is one, then the page paragraph, then the form, then the salary links (the calculator page keeps its form on top and its note below it; the page order is the keyboard order, with no CSS reordering). While a new calculation loads on a salary page the old answer stays in place, faded and unusable, with a sweeping band on the Calculate button, so the form does not move; after Calculate the page paragraph is written again from the new answer, while the heading, breadcrumb and the previous, next, other salary and Learn more links stay as the page was built (they match its address); the calculator page clears the old answer instead. Above the heading each page also has a breadcrumb (Home / province / salary) and, under those links, a "Learn more about this estimate" row with the province hub, the methodology page and the province's main form page; both come from the `hub` and `learnMore` fields of the links in the data block (`src/state/salaryPageLinks.ts`), and `generateSalaryPages` takes a `published` set of the content pages in the build, so a form link appears only once that form's page exists. Every salary page is reachable by following plain links from `index.html`: the home page's static footer (written into `dist/index.html` by `build/salaryPages/home.ts`, the real `SiteFooter` markup, which React replaces with identical markup on load) links to the province hubs, and each hub links to every salary page that was written for its province. Adding a province to the list adds its hub's salary links with no other change; without an engine file no pages are written and the home page keeps no static footer. The tests are in `build/salaryPages/` and `src/state/`.

### Salary sweep for the hub charts

The same Python run writes, for every province, `sweep`: the figures only (salary, total deductions, income tax, take-home and the two chart figures `average_rate` and `marginal_rate`, all as decimal text, no trace) for every salary from $1,000 to $250,000 in $1,000 steps, then to $500,000 in $5,000 steps, plus the `extra` salaries of the sweep setting (three around the $2,000 Employment Insurance band, and a salary just either side of each edge of the narrow Ontario health premium steps, so the lines show each step at its true place and width): 323 points, with the units written once in `sweep_units`. The take-home figure, the total deductions and the two rates count income tax (T1 line 43500, so tax cuts such as the Ontario LIFT credit count), Canada Pension Plan (all three parts) and Employment Insurance as the Employment Insurance form sets it (T2204 line 16, which goes to T1 line 31200): nothing paid after line 43500 (the Canada workers benefit, the Employment Insurance refund, line 47900) is counted. `average_rate` and `marginal_rate` are the engine's own `average_tax_rate` and `marginal_tax_rate` for that salary (the same two figures the salary pages show). The engine rounds both rates to four decimals before it answers, and a display of one decimal must round the exact rate once (34.347% is 34.3%, not 34.4%), so the sweep, and only the sweep, asks the engine for seven places (`unrounded_rates()` in `engine_figures.py` widens that one rounding rule for the block; the pages' full answers stay exactly what the service gives). The same file holds, for the notes under the charts, `edges` (where the marginal rate changes between neighbouring sweep salaries, found by bisection on the engine's own marginal rate to the cent, so each salary is exact to the dollar: the sweep salary below, the last whole salary at the old rate, the first whole salary at the new rate and the new rate) and `facts` (parameters read from the engine's own 2026 dataset files, such as the Ontario surtax thresholds and the start of the BC and Newfoundland and Labrador reductions, and the Employment Insurance band above $2,000), so no figure in the notes is typed. The script derives `edges` and `facts` from the engine's answers and dataset files until tax-engine publishes them, and a test pins the sweep figures. The steps are one setting, `sweep` in `build/salaryPages/provinces.json`; `sweepSalaries()` in `src/state/hubCharts.ts` is the same list for the page code (`regularSalaries()` is the list without the extra ones, which the comparison slider steps through), and a test fails if the two differ. The build maps the file's sweeps with `provinceSweeps` (`build/salaryPages/sweep.ts`): only the provinces the salary build served, `provisional` from the API's list as for the pages, the units read through `readUnit` (so "CA$" shows as "$"), and a failure for a province whose points are not exactly the sweep salaries in order. Nothing is written as a separate file: `hubChartBlocks` (`build/contentPages/hubs.ts`) puts every served province's sweep in one JSON data block (`hub-charts-data`) at the end of each swept province's hub, checked with `parseHubChartsData` (`src/state/hubCharts.ts`) and capped at 200,000 characters. Income tax is the total payable (T1 line 43500, before credits paid to you). The province comparison reads the block (see Province comparison on a hub).

### Adding a province (for example Alberta or British Columbia)

1. Make sure `GET /v1/jurisdictions` returns the province code (with `VITE_SITE_URL` set, a listed province the API does not return fails the build; without it the province is skipped with a warning) and that the year you list is one the API can compute, otherwise the build fails naming the page. Put its adapter and wording in `src/adapters/` and register the adapter in `src/adapters/index.ts`; without one, the page uses the fallback adapter (no simple breakdown, every trace line in the advanced view).
2. Add one entry to the list in `build/salaryPages/provinces.json` (the Python step and `provinces.ts` both read it; the year is the file's one `year`): `code` (for example `CA-AB`), `slug` (for example `ca-ab`), `from`, `to` and `step`. The pinned tax-engine must declare the province's take-home figures and rates in its manifest, as tax-service needs.
3. Add its hub text (its own forms) to `provinceHubs` in `src/state/provinceHubs.ts`, its slug to `FOOTER_PROVINCE_SLUGS` in `src/state/siteLinks.ts` and its name to `strings.siteNav.provinceNames`; the build fails for a listed province with no hub text.
4. Run `npm run check`, then a build with `ENGINE_FIGURES_FILE` and `VITE_API_BASE_URL` set, and open `dist/ca-ab/<salary>/index.html` and `dist/ca-ab/index.html`.

No province is hub-only at present. A province the API does not serve yet but that should have a hub is instead listed in `PROVINCES_WITHOUT_SALARY_PAGES` in `src/state/siteLinks.ts` (the build passes it to `hubPages`, and a test fails if a province is in both it and `provinces.ts`): its hub is written after the listed ones, with no salary section and wording that promises no salary examples, and the federal form pages link it as "<name> forms". When the API serves it, move it into the list and out of `PROVINCES_WITHOUT_SALARY_PAGES`.

Nothing else changes: the pages, their canonical addresses, the sitemap, the links between pages and the hub's salary links all come from that one list. A test adds a made-up province to the list to show this (`build/salaryPages/crawl.test.ts`), and `build/salaryPages/pageFigures.test.ts` checks that each page carries the figures the engine gave for its own salary. A deploy build asks the API only which jurisdictions it serves, so the API must be up when the site is built; `build/localEngine/engineFigures.test.ts` checks the file the Python step wrote (CI's `engine-figures` job).

## Content pages

Reading pages (hubs, form pages, the methodology page) share one shell: `src/components/ContentPage.tsx` renders the heading, the Light/Dark switch, a breadcrumb row (the shared `src/components/Breadcrumb.tsx`, also used by salary pages), the sections and the site footer. The footer (`src/components/SiteFooter.tsx`) is on every page, the calculator and the salary pages included: links to "How we calculate" and the provinces above the unchanged disclaimer, with the words in `src/strings.ts`.

**Adding a page** is one entry in the list in `src/state/contentPages.ts`: `slug` (for example `ca-on` or `forms/bc428`), `title` (under 64 characters; salary pages stay under 60), `description` (under 160), `heading`, an optional `lede`, a `trail` (the listed pages between Home and this one, each given as a label and a slug) and the `sections` (a heading and its blocks each). A block is one of six kinds: a `paragraph` (words with optional links in the middle, made with `paragraph(...)`), a `list` of entries with a label, an optional link and a description (an optional title shows as a small heading), `links` (a labelled `nav` with a list, laid out as a `grid` of buttons or a `row`) or a `table` (a caption, column headings and rows). A hub also has a `salaryCharts` and a `provinceComparison` block, each only a data reference carrying the hub's slug. Page copy is written in `src/state/contentPages.ts` or `src/state/provinceHubs.ts`, never in a component. The build refuses an invalid or repeated slug, a title or description over the limit, and a trail step that is not itself a listed page, a table row that does not have one cell per heading, an empty list, links block or table, and then writes nothing. Run `npm run check`, then a deploy-style build, and open `dist/<slug>/index.html`.

**Province hubs:** each province has a hub page at its slug (`/ca-on/`) that explains how its take-home is worked out, lists its forms and the federal forms it uses, links every salary page that was written for it and links the other hubs and the methodology page. The text is in `src/state/provinceHubs.ts` (the province name always comes from `strings.siteNav.provinceNames`), and `build/contentPages/hubs.ts` builds one hub per entry of `build/salaryPages/provinces.ts`, in that order, then one for each province in `PROVINCES_WITHOUT_SALARY_PAGES` (`src/state/siteLinks.ts`; no salary section, wording that promises no salary examples), from what the salary build wrote: in a build without `VITE_SITE_URL`, a province the API did not return still gets its hub, with no salary section (with it set, the salary build has already failed), and a listed province with no hub text fails the build. A form is linked only when its page (`forms/<id>`, from `formSlug` in `src/state/siteLinks.ts`) is one of the pages written, so no link is ever broken. The switch slot id is in `src/state/themeSlot.ts`, so the calculator never imports page copy.

**Quebec's hub** has its own wording, as `words` on its entry in `src/state/provinceHubs.ts`: the take-home paragraph (five things: income tax, the Quebec Pension Plan, Employment Insurance at the Quebec rate, Quebec Parental Insurance Plan premiums and the Quebec prescription drug insurance premium), the one line under each chart, and replacements for the shared federal entries by form id. Its Schedule 8 is listed under the id `schedule-8-qc`, so it never links the Canada Pension Plan page; give the Quebec page that id when it exists. `words` is a function of the province's name (from `strings.siteNav.provinceNames`) and wins over `taxReduction`: Quebec's chart lines are written out whole. Quebec says QPP and QPIP, never CPP. Its chart notes are `src/state/hubNoteText/ca-qc.ts`, written whole rather than from the shared note helpers because the shared wording names the Canada Pension Plan and Quebec's structure differs (QPIP from $2,000, the drug premium); every figure is read from the engine's sweep like the other provinces', except the printed rates and maximums the file declares. Quebec's salary pages come from its own adapter, `src/adapters/ca-qc.ts` (not `adaptCanadian`: its pension plan, parental insurance and drug premium differ, and its federal tax is the line before the Quebec abatement), which hands the page its own sentences as `AdaptedResult.wording` (`strings.adapters.caQc`): the page description and paragraph and the three answer-card help texts. The drug premium has its own row, so the total income tax row is federal plus Quebec tax only and the seven rows add up to the engine's total taken off. The advanced view still prints the engine's own form lines as sent, including the federal CPP and T2204 forms its Quebec trace runs. The README's list of provinces changes when the API serves Quebec. Quebec's hub and its salary pages are released together; its `CA-QC` entry in `build/salaryPages/provinces.json` needs the API to list Quebec (tax-service #94), and a deploy build without it skips the province with a warning.

**Rates pages:** a province with wording in `src/state/ratesPageText/` and a sweep gets `/ca-xx/tax-rates/` (no year, so links last across years; `build/contentPages/rates.ts` writes the page, `ratesPages`). The page is four sections of typed blocks: the opening finding and the chart (`ratesPart` and `ratesChart`), "How to read these salaries", the notes grouped by salary range, each with its "Caused by" form links, and the bracket tables. Every word is read from the hub's own data block (the page carries the same sweep block as the hubs), and every figure in it is a spec resolved from the sweep (`src/state/hubNotes.ts`, kinds `n h w x` added for this page), so no figure is typed. The chart (`RatesChart`) always starts at $0, opens at $150,000 and has a slider for the highest salary in $50,000 steps to $500,000; the $2,000 Employment Insurance band is left out of the vertical scale and a note says where it goes off the top; the figures table is the closed "Show the figures as a table" under the chart and holds every point. Nothing is picked on load: `?salary=` (read after hydration) picks one point, and only "Link to this salary" writes it to the address; the slider never touches it. Adding a province is a text file there, its facts in `engine_figures.py`, and an entry in `ratesPageText` in `src/state/ratesPage.ts`. The new address is not a file: the CloudFront function rewrites an address with no extension to `/index.html`, so check how `/ca-on/tax-rates/` is served the way `/ca-on/` is before release.

**Hub chart sections:** a hub with a sweep has three chart sections, in this order: the take-home chart inside the existing "How your {province} take-home is worked out" section (`#take-home`), then Average tax rate (`#average-rate`), and Marginal tax rate (`#marginal-rate`), each a card with a heading, one line and the chart (the take-home chart sits in its existing card under its own "Take-home pay" sub-heading and line); a section with an `id` gets a permalink beside its heading. Each chart is a typed `salaryChart` block with its own slot (`HUB_CHART_SLOT_IDS`), prerendered and hydrated by itself in `src/contentMain.tsx`; the charts share their marker and the Per year / Per month choice through `src/state/hubChartView.ts`, so the three slots behave as one. The province's own text (#288) goes after each chart block, as a `chartNotes` block: `src/state/hubNotes.ts` resolves the `{figures}` of the bullets in `src/state/hubNoteText/` (shared wording and one file per province) from the hub's data block: a rate or an amount at a sweep salary, a change of the marginal rate (an engine `edge`, named by a salary near it, so the figure shown is the engine's) or an engine `fact`; only amounts printed on a form (`d:`) and a few words (`l:`) are declared, and `src/state/hubNotes.test.ts` fails when a note names a change or a fact the data does not hold. The average and marginal rate charts read the rates of the sweep, and take-home the take-home column.

**Form pages** (`/forms/<id>/`) are content pages drawn from one list, `formPages` in `src/state/formPages.ts`. Adding a form is one file in `src/state/forms/` (copy `on428.ts`; `figuresOf` gives the two figure helpers) and one entry in that list: `id`, `name`, `province`, `year`, the example salary as text, a title, description and plain intro, and the `sections`. Each section has a readable `id` (its permalink, such as `#credits`; unique on the page), the `lines` it covers, ONE paragraph and a worked example, and optionally `links`: a short row of `ContentLink`s after the example, for a part that points at another form's page (build the address with `contentPath(formSlug(id))`, never by hand). Write a figure as `{name}` in the words and declare it in the section's `figures`: either a result of the saved answer (`trace`: its form and step label) or a figure the form prints (`printed`: words that appear in that form's steps). The words of a form live in its file, not `strings.ts`, like the methodology page's. A test reads the saved answer in `src/api/fixtures/` for the page's province, year and salary and fails if a quoted figure differs or a section id repeats. A form page's `trail` is empty: the province pages are written by the build, not listed in `contentPages`, and a trail step must be a listed page; the related row links to the province page by address, and to the example salary page only when the build wrote that page, as the hubs do for forms. The page's styles, `FormSections.module.css`, are imported by `src/contentMain.tsx` like the shell's.

**Province comparison on a hub:** a hub whose province has a sweep carries a section with a `provinceComparison` block (`{ kind: 'provinceComparison', province }`, the hub's slug and nothing else). `ContentPage` draws it, in a slot with the id in `src/state/hubSlots.ts` and the province in `data-province`, from the hub's data block (every served province's sweep, `parseHubChartsData`); `src/contentMain.tsx` mounts the same `ProvinceComparison` into that slot from the same block, so nothing is fetched and a test (`src/contentMain.test.tsx`) fails if the mounted markup differs from the written. It has its own measure switch and salary (`SalarySlider`: a slider with one step for each point of the data, so no second list of steps, and a typed box that snaps to the nearest point), shares nothing with the charts above it, and shows the API's figures through `src/money/format.ts`; the bars' lengths and the nearest point come from `src/money/scale.ts`, the order from `compareAmounts`. A bar links to another province's hub only because every swept province has a hub (`hubPages` fails otherwise). The words are `strings.hubCharts.comparison`.

**Where a page lives** is said in one place, `src/state/siteLinks.ts`: the address, the file path below `dist/`, the slug rules, the home address and the footer's province slugs (their names are in `strings.siteNav`). Changing the shape of a content page's address is a change there. The salary pages keep their own address function (`build/salaryPages/address.ts`) and file shape, and the home page is `/`; a content slug that looks like a salary page address is refused. Adding a province to `build/salaryPages/provinces.ts` does not add it to the footer: add its slug to `FOOTER_PROVINCE_SLUGS` and its name to `strings.siteNav.provinceNames` (see "Adding a province"). Each page gets its own title, description, canonical link and `og:url`, an entry in `dist/sitemap.xml` and a `lastmod` by the same rule as the salary pages (`build/contentPages/`).

**Theme:** the page loads `/theme-init.js` in the head, like the calculator, so a stored Light or Dark choice shows before first paint. Content pages are built from their own template, `content.html` (the calculator's head with an empty `#root`), whose only script is `src/contentMain.tsx`: it finds the `#content-theme-toggle` slot in the pre-built page and mounts the switch there, and on a hub the salary charts card and the province comparison into their own slots, so the page does not load the calculator and sends no visit beacon. `src/main.tsx` is the calculator's entry and the only place the visit beacon (`src/beacon/visitBeacon.ts`) is started. The two share React in one chunk. The build reads `dist/content.html` to write the pages and then deletes it, so it is never deployed (the content entry imports the sheets of `Breadcrumb`, `ContentPage`, `FormSections` and `SiteFooter`, which the page only pre-renders; `build/keepCssModules.ts` stops the build dropping a sheet imported only for its styles); keep its head in step with `index.html` (`build/contentPages/template.test.ts` checks).

**When pages are written:** only in deploy builds, with `ENGINE_FIGURES_FILE` set (and `VITE_API_BASE_URL`, for the list of jurisdictions), together with the salary pages; local builds and CI write none.

**Not-found page:** a deploy build also writes `dist/404.html` (`build/contentPages/notFound.ts`, text in `src/state/notFoundPage.ts`), a text-only page that links home, the province hubs and the methodology page. It has no canonical or `og:url`, carries `<meta name="robots" content="noindex">`, and is never in the sitemap; it is not one of the listed content pages.

**CDN:** the pages are folders (`/ca-on/`, `/forms/bc428/`, `/methodology/`), so the CDN must serve those extension-less paths, with and without the trailing slash, as the pre-built `<path>/index.html`. This may need a change in the infrastructure repository (tax-infra). Until then the footer links to pages that later tickets add are links to paths the CDN does not yet serve.
